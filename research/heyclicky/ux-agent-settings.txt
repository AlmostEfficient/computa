WORKING-DIRECTORY RESOLUTION FALLS BACK WHEN CUSTOM FOLDER IS MISSING
The preference consumer FUN_101f5baac resolves a working-directory path through FUN_101fa2e60. A present, nonempty custom path is returned only if the same existence-and-directory predicate FUN_101fa33fc succeeds. Otherwise resolution calls the codexHomeManager directory-preparation helper FUN_101f36470 and obtains its default directory URL through FUN_101f35f4c. The preparation helper requests createDirectoryAtURL with intermediate directories enabled. It can throw on failure; the complete visible error handling is not established here. No custom-path rewrite appears in the resolver, consistent with the saved stale override remaining available to Reset.
Resolution is cached: FUN_101f5baac compares the current optional preference with the cached preference and reuses the cached result when they match and cache age is less than five seconds. A changed preference or an older/missing cache resolves again and stores the new result/time. Thus deletion of the chosen directory need not be detected on every immediate call; the existence check is bypassed on a matching fresh cache hit. This is call-time cache expiry, not a five-second polling timer.
The default URL helper queries directory code 0xe in domain 1, then appends two stored path components. The component values are not yet traced, so the exact default pathname is not asserted. Numerous callers consume FUN_101f5baac; their full task-launch priority rules are not yet mapped. This verifies the shared resolver's fallback, not that every existing or new task always chooses this resolver over a thread-specific path.

QUIET MONITOR CADENCE AND EXIT PRESENTATION
On quiet-context exit, FUN_10143a5f0 simply calls the shared notch presentation resolver FUN_10142375c. It does not itself replay speech, iterate finished jobs or issue notifications. Therefore the verified effect is reevaluating notch presentation; any queued-work behavior depends on the resolver's current-state branches.
Monitor starter FUN_101dfd924 cancels an existing quietContextMonitoringTask and schedules/stores descriptor 10322bac8. That descriptor resolves to FUN_101dfead0 -> FUN_101dfdb9c -> FUN_101dfdc80. The loop checks cancellation and weak-manager availability before proceeding. When the numeric activity metric from FUN_102746d38 exceeds 120, it skips inspection and sleeps 20 seconds. Otherwise it awaits quiet-context inspection FUN_101dfc9ac, then also sleeps 20 seconds before repeating. The 20-second value is a requested sleep after processing, not an exact fixed-rate timer or maximum detection latency. The loop terminates on cancellation or missing manager.
FUN_102746d38 incorporates globalPushToTalkShortcutMonitor.lastObservedKeyboardActivityTime alongside another elapsed-activity measure; the complete event mapping remains unverified. Do not label the skip gate as exclusively keyboard idleness. Skipped checks leave the previously observed quiet context in place in this loop. Other direct checks may update it; this cadence is not a claim that the whole app only detects context once every 20 seconds.
Evidence: evidence/ux/quiet-context-exit-presentation.json, quiet-context-monitor-start.json, quiet-context-monitor-loop.json and quiet-context-idle-gate.json. No monitor or sensor access performed; static code inspection only.

QUIET MONITOR ACTIVITY METRIC AND SETUP LINK
FUN_102746d38 takes the minimum seconds-since-last-event across eight CoreGraphics event types (raw values 5, 1, 3, 25, 6, 7, 27 and 22), using CGEventSourceSecondsSinceLastEventType with source-state argument 1. If the shortcut monitor has a lastObservedKeyboardActivityTime, it also takes the minimum with elapsed time since that Date. Thus the earlier >120 gate is based on the most recent activity among these measured sources, not solely keyboard inactivity. Exact event-type naming and platform reporting limitations are not asserted here.
The retained export's direct caller of quiet monitor starter FUN_101dfd924 is manager setup FUN_101fd86c4, already linked to ordinary launch in the browser-integration investigation (ux-history.txt). The background loop therefore has a setup entry rather than being only a settings-screen operation. This does not establish behavior after every lifecycle change or prove a hard response-time bound: the loop's 20-second sleeps and idle skipping can preserve old context until a later check, and independent callers may refresh sooner.
