HEYCLICKY VOICE AND DICTATION UX — PARTIAL
Scope: app UX only, billing excluded. Evidence is offline retained decompilation for 1.1.3 build 71; no recording, keyboard action, app launch or target request was performed.

CURRENT USER FLOW SUMMARY
- Settings separates speaking to HeyClicky from inserting dictated text, with held and hands-free dictation shortcuts.
- Dictation checks Accessibility and microphone access. The first microphone prompt's completion does not itself restart the attempt.
- Held recording shows Dictating; hands-free shows Dictating (hands-free). A conditional quick second press can lock recording hands-free.
- Normal finish publishes Transcribing. Escape takes a separate cancellation path and invalidates late results.
- An empty/whitespace result ends the session and clears the status without inserting text or replacing the clipboard.
- Available text can be inserted or fall back to manual paste. Partial text can also be salvaged after failure.
- Clipboard recovery offers Copied to your clipboard / Press ⌘V to paste in a notch notice with an X and a six-second auto-hide path. Dismissing the notice preserves clipboard text.

These are static code-backed flows, not live usability observations. Remaining material gaps: physical shortcut recognition/defaults, full voice-assistant behavior, insertion targeting and success verification, some callback presentation, and rendered/accessibility behavior. Historical “unresolved” notes below are superseded only by later explicit evidence sections.

SETTINGS EXPLAINS FOUR DISTINCT SHORTCUT ACTIONS
HomeSpaceSettingsContent functions 10078a018 and 10078a710 construct shared rows through 10078a4d8 with action identifiers 0, 1, 2 and 3. Label function 10039375c independently agrees with the mapping.
0 Push to talk: “Hold to talk to HeyClicky. Release to send.”
1 Text mode: “Press to type to HeyClicky instead of talking.”
2 Dictate: “Hold and speak. Release to insert what you said at your cursor.”
3 Hands-free dictation: “Dictate without holding a key down. Press to start, press again to stop.”

This establishes the user-facing distinction between asking the assistant and inserting dictated text, and between held and toggled recording. These strings describe intended behavior; they do not alone establish capture timing, transcription success, insertion destination preservation or delivery guarantees. They also do not identify default key combinations. In particular, do not conflate hands-free dictation with an always-listening assistant conversation.

SHORT RELEASE, SECOND PRESS AND HANDS-FREE LOCK
The controller pair 1021bf738 / 1021bfefc now establishes the short-press behavior beyond isolated constants. In the held mode, release computes time since holdPressStartTime (missing timestamp defaults to 1.4 seconds). Below 0.08 seconds, if no bounce-release work is pending, it schedules an 0.08-second retry via 1021cf240 -> 1021c4198; that callback clears the pending slot and re-enters the release handler. A new press while that bounce work is pending cancels it and returns, preserving the current capture instead of treating the bounce as a fresh gesture.

After that handling, releases shorter than 0.4 seconds can schedule pendingQuickTapFinishWorkItem with a 0.4-second delay, but only if isDedicatedHandsFreeShortcutConfigured is false and isOnboardingTutorialActive returns false. Otherwise release clears the mode and calls shared finish 1021c36f0 immediately. Delayed callback 1021cf1dc -> 1021c4278 clears the pending slot and mode, then finishes. These thresholds describe input handling, not a minimum usable speech length.

If another press arrives while the quick-tap finish is pending, 1021bf738 cancels that work item, clears the held-press timestamp, switches mode to 2, and publishes “Dictating (hands-free)”. That is the controller's double-tap-to-hands-free route. A later press in mode 2 stops through shared finish and sets shouldIgnoreNextReleaseAfterLockStop; the following release consumes and clears that flag, preventing duplicate finishing. A press in idle starts through the permission gate and records holdPressStartTime only if recording became active.

Metadata provides a matching ShortcutTransition enum (1035ab46c) with none, pressed, released. The subscription's exact generic type binding remains to verify before calling enum-order evidence alone a proof of the numeric producer mapping. The handler behavior and named pending-work fields support the press/release interpretation; low-level physical key recognition remains a separate gap. No live timing was measured.

Evidence: evidence/ux/dictation-held-and-toggle-operations.json, dictation-short-press-callbacks.json, dictation-shortcut-event-chain.json and evidence/swift-type-fields.json. This resolves the earlier open 0.08/0.4-second branch semantics at the controller level.

ESCAPE — CANCELS ACTIVE DICTATION, DOES NOT USE NORMAL FINISH
Shared Escape router 1021df1d8 reaches controller handler 1021cc494 after earlier takeover/guidance and other priority checks. When controller recording flag +0x1d8 is true, this handler invokes 1021cc128 and reports the event handled. When false it reports unhandled. Therefore the statement applies when Escape reaches this active-dictation branch, not to every Escape anywhere in the app.

Cancellation 1021cc128 increments session value +0x1e0; cancels and clears pending controller work; invokes microphone cleanup 101c1a7e4; calls transcriber cleanup 1027d84c0 when present; clears capture/focus context; sets recording false; resets mode and gesture timers through 1021c438c; and clears the current status message. The gesture cleanup cancels both pendingQuickTapFinishWorkItem and pendingBounceReleaseWorkItem, resets holdPressStartTime and the ignore-release flag. This path does not call normal finish 1021c36f0, insertion handler 1021c8910, or clipboard-recovery helper 1021d06c4. Do not describe Escape cancellation as submitting the dictation or salvaging it to the clipboard.

Microphone helper 101c1a7e4 clears its captured-audio handler and buffer/converter state and schedules capture-session cleanup; actual device shutdown completion remains to trace. No claim is made that previously streamed audio is retracted.

Late-result protection is present in 1021c8910: it compares the supplied session value with current controller +0x1e0 and returns immediately on mismatch before processing/inserting text. Because cancellation increments that value, an old result reaching this handler is discarded. This verifies the guard on this result path, not every possible asynchronous callback or a result already inserted before cancellation.

EMPTY RESULT — CLEANUP WITHOUT INSERTION OR CLIPBOARD REPLACEMENT
After accepting the session value, result handler 1021c8910 calls cleanup 1021cd9e0, trims surrounding whitespace/newlines from the result, and checks whether the trimmed string is empty. Empty text clears the status through 1021c35d0 and returns before insertion, clipboard fallback, or the later nonempty-result timestamp write. This handler does not emit a “no speech” error for that branch. Empty transcription is not proof that the person was silent: the source result could be empty for other reasons.

Cleanup 1021cd9e0 increments the session value, cancels pending controller work, invokes microphone/transcriber cleanup, clears active session references, sets recording false, and resets input mode and gesture timers through 1021c438c. Thus empty results finish the controller session rather than leaving its recording flag active. This still does not measure physical microphone shutdown latency.

Evidence: evidence/ux/dictation-stop-copy-candidates.json (1021c8910), dictation-result-cleanup.json and dictation-escape-cancel.json (shared microphone cleanup). The early empty branch has no clipboard write, so prior clipboard contents remain untouched through this branch.
