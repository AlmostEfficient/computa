MARKDOWN LIVE-UPDATE TIMING AND REPLACEMENT LIMITATION
Watcher event handler FUN_1029cc57c -> FUN_1029cbe50 invokes FUN_1029cc5e4 for each received event. That helper cancels the previous pending reload work item, replaces it, and schedules the new item on the main queue for now + 0.15 seconds. Its callback FUN_1029ccb7c -> FUN_1029ccaa0 invokes onFileChanged, already linked to model reload. This coalesces bursts of edits; 150 ms is a requested scheduling delay, not a measured time until visible rendering.
For delete or rename events, the same handler additionally cancels and clears the old dispatch source and schedules a weakly captured reattachment callback for now + 0.2 seconds. FUN_1029cd2f8 -> FUN_1029cc944 -> FUN_1029cb53c attempts to open the original watched path again. This supports editors that replace a file while saving. The callback does not itself trigger a second reload: the earlier 150 ms callback and 200 ms reattachment are distinct. If the replacement is not readable at the reload time, the load may fail even if watcher reattachment later succeeds; actual load timing and error visibility depend on the asynchronous model. If the path still cannot be opened at reattachment, setup returns and this chain schedules no further attempt. Therefore do not claim indefinite recovery after deletion or arbitrary delayed replacement.
Watcher destruction FUN_1029cbc80 cancels both the pending reload item and existing dispatch source before releasing stored fields. This establishes teardown cleanup without resolving the separate missing argument in the view's onDisappear setter.
Evidence: evidence/ux/document-watcher-events.json and document-watcher-callbacks.json. Delay constants decoded as IEEE-754 doubles: 0x3fc3333333333333 = 0.15 and 0x3fc999999999999a = 0.2. Static evidence only; no file edits or app execution performed. These findings supersede the earlier unresolved watcher timing and reattachment notes.
